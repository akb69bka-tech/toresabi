# 公開したあとの直し方とアップデートの出し方（Claude に頼むだけにする）

作成日: 2026年10月20日。アプリを公開したあとは「利用者の声を集める → 直す → 新しいバージョンを App Store に出す」のくり返しです。この文書は、そのくり返しを **Claude に頼むだけで回る**ようにするための準備と、毎回の頼み方です。

---

## 1. 全体の流れ

```
利用者の声（App Store のレビュー・アプリの「ご意見を送る」メール・家族の感想）
   ↓ あなた: Claude に貼る（または GitHub の Issue に書く）
Claude: 原因を調べて直す → テスト → PR（変更のまとめ）を作る
   ↓ あなた: GitHub で「Merge」を押す
Claude: 「バージョン 1.1.1 で申請して」と言われたら、GitHub Actions（自動の組み立て）を起動
   ↓ 自動: iPhone アプリを組み立てて App Store Connect にアップロード（10〜30分）
あなた: App Store Connect で新しいビルドを選び、「審査へ提出」を押す（ここだけは人がやる決まり）
   ↓ Apple の審査（通常1〜3日。出典不明）
公開
```

Mac も Xcode も、2回目からは不要です（最初の申請だけは `申請チェックリスト.md` のとおり Mac が必要です）。

---

## 2. 一度だけやる準備（30分）

### A. App Store Connect の API キーを作る（自動アップロードの鍵）

1. https://appstoreconnect.apple.com/ → 「ユーザとアクセス」→「統合」タブ →「App Store Connect API」→「チームキー」の ＋
2. 名前: `github-actions`、アクセス: **App Manager**。「クラウド管理による配布証明書へのアクセス」のような項目があれば **オン**にする（CI が配布用の証明書を Apple 側で管理できるようになり、Mac から証明書を持ち出さなくて済む。**要確認**: 表示される名称は Apple の画面で変わります）
3. 作成後に **.p8 ファイルを1回だけダウンロード**できます（なくしたら作り直し）。同じ画面の **Issuer ID** と **キー ID** をメモ
4. Team ID: https://developer.apple.com/account → 「メンバーシップの詳細」の **Team ID**（10桁）

### B. GitHub に Secrets を登録する

GitHub のリポジトリ → Settings → Secrets and variables → Actions → New repository secret で、次を登録:

| 名前 | 中身 |
| --- | --- |
| `APPLE_TEAM_ID` | Team ID（10桁） |
| `ASC_KEY_ID` | API キーのキー ID |
| `ASC_ISSUER_ID` | Issuer ID |
| `ASC_API_KEY_P8` | .p8 ファイルをテキストエディタで開いた中身（`-----BEGIN PRIVATE KEY-----` から最後まで） |
| `REVENUECAT_API_KEY` | RevenueCat の Apple 用 公開APIキー（`appl_` で始まる）。これを入れると課金が有効になる |
| `SUPPORT_EMAIL` | 「ご意見・不具合を送る」の宛先メールアドレス |

Secrets は GitHub の中だけに保存され、Claude からも見えません（ワークフローの実行時にだけ使われます）。

> 署名でエラーになった場合（ログに `No signing certificate` など）: Mac の Xcode → Settings → Accounts → Manage Certificates で **Apple Distribution** 証明書を作り、キーチェーンアクセスから .p12 で書き出して、`IOS_DIST_P12_BASE64`（`base64 -i 書き出した.p12 | pbcopy` の結果）と `IOS_DIST_P12_PASSWORD` を Secrets に追加してください。

### C. 動くか一度試す

GitHub → Actions タブ → 「iOS release」→ Run workflow → version に `1.1.0` を入れて実行。緑になれば、App Store Connect の TestFlight に新しいビルドが届きます。赤になったら、そのログの URL を Claude に貼ってください（直します）。

### D. GitHub Actions の料金

公開リポジトリなら無料です。非公開リポジトリは無料枠（月2,000分。macOS は10倍で消費するので実質 200分 ≒ 1回15〜25分 × 8〜12回/月）を超えると有料になります（出典: GitHub の料金ページ https://docs.github.com/ja/billing/managing-billing-for-github-actions/about-billing-for-github-actions 。**金額は変わるので確認**）。

## 3. 利用者の声を集める（回収）

> **相談する場所と担当チーム**は `ios-app/サポート体制.md` にまとめました（お客様の声チーム・不具合解消チーム・Apple 窓口チーム）。迷ったら GitHub の常設 Issue「【ご飯帖 サポート窓口】」（#12）にコメントし、Claude に「/support #12」と頼んでください。

| 入口 | しくみ | Claude への渡し方 |
| --- | --- | --- |
| App Store のレビュー | App Store Connect → アプリ → 「評価とレビュー」。返信もここから | 気になるレビューをコピーして貼る |
| アプリの「ご意見・不具合を送る」 | 設定の一番下のボタン。`SUPPORT_EMAIL` 宛てに、アプリのバージョン・国・言語・機種が自動で添えられたメールが開く | メールの本文を貼る |
| クラッシュ（落ちる） | App Store Connect → 「App Analytics」/ Xcode Organizer の「Crashes」 | 「何をしたら落ちた」と機種・iOS のバージョンを伝える |
| 使われ方の数字 | App Store Connect → 「App Analytics」（ダウンロード数・お試し開始数・有料転換率・解約率） | 月に一度スクリーンショットを貼ると、値段や無料期間の見直しを一緒に考えられます |

**自動化の次の一手（希望があれば設定します）**: App Store Connect API キーを Claude の環境に登録すれば、週に一度レビューを自動で取りこんで、要望と不具合を GitHub の Issue にまとめる「定期タスク」を作れます。その先は、Issue を見て直す → PR、までを定期タスクで回せます。

## 4. 毎回の頼み方（例）

- 「レビューに『買い物メモが消える』とあった。直して」 → Claude が原因を調べ、直して、テストして、PR を作ります
- 「フランスのレシピにこれを足して」 → 同じく PR
- 「1.1.1 で申請して」 → Claude が `ios-app/package.json` のバージョンを上げ、`metadata.md` の「このバージョンの新機能」を書き、ワークフローを起動します。アップロードが終わったら、App Store Connect で「審査へ提出」を押してください
- 「値段を 380円にしたい」 → App Store Connect で価格を変えるだけ（アプリは実際の価格を自動で表示）。説明文と試算は Claude が直します

### バージョン番号の決め方

- 直しだけ: 1.1.0 → **1.1.1**
- 新しい機能: 1.1.1 → **1.2.0**
- 大きな作り直し: **2.0.0**

ビルド番号は GitHub Actions の実行番号が自動で入るので、気にしなくて大丈夫です。

## 5. 公開後に見る数字

App Store Connect →「App Analytics」→「サブスクリプション」で、お試し開始率（ダウンロード → 無料お試しを始めた人）、お試し → 有料になった割合、月の解約率を月に一度見て、Claude に貼ってください。値段や無料期間の長さ（App Store Connect で変えるだけ）、案内の文言の見直しを一緒に考えます。

## 課金中に不具合が起きたら（公開後の対応の流れ）

| 起きたこと | 利用者に起きること | あなた（と Claude）がすること | かかる時間 |
| --- | --- | --- | --- |
| 献立やレシピの表示などの不具合（課金とは無関係） | 会員のまま使いにくくなる。料金は Apple が自動で請求し続ける | ① `remote.json` の `notice` に「◯◯の不具合を確認中。△日に修正版を出します」を書く（審査なし・次の起動から表示）→ ② Claude に直させて「1.1.1 で申請して」→ ③ 審査で「Expedited Review（優先審査）」を申請（App Store Connect の「お問い合わせ」から。重大な不具合なら数時間〜1日で通ることが多い。出典不明） | 通知: 数分／修正版: 半日〜3日 |
| 購入したのに使えない（課金の不具合） | 「購入を復元」で直ることが多い。直らなければ払い損の状態 | ① サポートページの案内どおり「設定 → 購入を復元」を試してもらう → ② RevenueCat の Customers 画面でその人の購入が有効か確認 → ③ アプリ側の問題なら修正版を優先審査で出す | 復元: 即時／修正版: 半日〜3日 |
| 返金してほしいと言われた | **返金は Apple が行います**（開発者は直接返金できません）。利用者は https://reportaproblem.apple.com/ から申請し、Apple が可否を決めます。返金された分は、あなたへの入金から差し引かれます | 利用者にその URL を案内する。App Store Connect の「返金リクエスト」の通知（Consumption API）に答える設定にしておくと、Apple の判断材料になります（任意） | Apple の判断: 数日 |
| 大きな不具合で、一時的に配信を止めたい | 「価格および配信状況」で「配信を停止」すると新規のダウンロードは止まる。**すでに入っているアプリと購読はそのまま残り、請求も続く** | 停止は最後の手段。先に `remote.json` の `notice` で知らせ、修正版を優先審査で出す方が利用者の不利益が少ない | — |
| RevenueCat や通信が止まった | 購入状態はアプリの中に保存しているので、**会員はそのまま使えます**（起動時の確認に失敗しても、前回の状態を使う作り） | 復旧を待つだけでよい。長引くときは `notice` で知らせる | — |

### いまの作りで、被害を小さくするために入っているもの
- 購入状態の端末内キャッシュ（通信が切れても会員のまま）
- 「購入を復元」ボタン（購入画面と設定）
- `remote.json`（審査なしでお知らせ・課金まわりの切りかえ・古いバージョンへの更新案内を出せる）
- 「ご意見・不具合を送る」ボタン（バージョン・国・機種が自動で添付される）と GitHub の Issue フォーム
- GitHub Actions で半日以内に修正版を Apple に送れる（Secrets 登録後）

### 気をつけること
- 利用者に「返金します」と自分で約束しない（返金の決定権は Apple にあります）。「Apple に返金を申請できます」と案内する
- 不具合の期間が長引いた場合に「1か月分を補償する」ようなことをしたいなら、App Store Connect の「オファーコード」（無料期間のコードを配る）が使えます
- 法律面（消費者契約・特定商取引法）は App Store の規約に従う形ですが、個別の判断は専門家に確認してください（**わかりません**）

## 6. 審査に出さずに直せること・直せないこと

| 直したい内容 | 審査 |
| --- | --- |
| 価格・無料期間・配信する国・説明文・スクリーンショット | **不要**（App Store Connect で変えるだけ。説明文は次の審査時に反映されるものもある） |
| アプリ内のお知らせ（「○日にメンテナンス」「新しいバージョンをどうぞ」など）、無料期間のしくみの切りかえ、1年ありがとう価格を出す時期 | **不要**。`gohancho/remote.json`（main ブランチ）を直すだけ。アプリは起動時に読んで、次に開いたときから反映（Claude に「お知らせを出して」と頼めば直します） |
| レシピ・翻訳・画面の文字・不具合・新機能 | **必要**（アプリの中身が変わるので、上の流れで新しいバージョンを出す） |

アプリの中身を審査なしで差しかえる「ライブアップデート」のしくみ（Capgo など）もありますが、Apple の規約の範囲が分かりにくく、最初は使いません。アップデートの回数が増えて困るようになったら検討します。

## 7. 自己検算と注意

- GitHub Actions の macOS 上で Apple の「クラウド管理の配布証明書」が API キーだけで使えるかは、Apple の仕様変更で変わることがあります（**要確認**）。失敗したときの逃げ道（.p12 の登録）を上に書きました。
- ワークフローはこの環境では実際に動かしていません（macOS の実行環境と Apple のアカウントが必要なため）。最初の実行（2-C）で赤になったら、ログを貼ってください。
- 「審査へ提出」は人が押す前提です。これも API で自動化できますが、間違ったビルドを出してしまう事故を防ぐため、最初は手で押すことをすすめます。
